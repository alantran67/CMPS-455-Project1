## Alan Tran, Dining Philosophers
---
For the Dining Philosophers task, Alan's main responsibility was creating the synchronization logic and making sure it could later be integrated into the rest of the group project. He kept the Dining Philosophers program in its own class instead of putting everything inside Main.java. By separating his part into its own class and providing a run() function, Brendan could connect Alan's task to the command-line program without having to rewrite his synchronization code.

The first part he had to think about was how to represent the philosophers and chopsticks. Each philosopher needed to behave independently, so he created them as separate threads. The chopsticks were shared resources between the philosophers, which meant Alan needed some way to make sure two philosophers could not use the same chopstick at the same time. He used semaphores for this because they allow a thread to acquire a shared resource and force other threads to wait until that resource is released. This gave him a way to control access to each chopstick while still allowing multiple philosophers to run at the same time.

One of the biggest issues Alan had to consider was deadlock. If every philosopher picked up one chopstick and then waited for the second chopstick, every philosopher could become stuck waiting forever. Because of this, he could not just let every thread acquire its chopsticks without additional synchronization. He had to design the program so that philosophers could still compete for chopsticks while preventing the situation where all of them became permanently blocked. This was probably the most important part of the task because the program could appear to work at first, but still eventually freeze if the synchronization was not handled correctly.

Another challenge was the shared meal count. The user enters a total number of meals, and the philosophers are only supposed to eat that many meals altogether. Since several philosopher threads can be running at the same time, they could potentially check the meal count at nearly the same moment. Without synchronization, two philosophers might both believe another meal is available and cause the total to go past the requested amount. Alan had to make sure that checking and updating the meal count was handled safely so that the final number of meals would never exceed the value entered by the user.

He also had to think about the beginning and ending of the philosopher threads. The assignment required the philosophers to be coordinated rather than simply starting and finishing at completely different times. Alan needed the threads to enter properly before the main dining activity and also make sure the program did not finish while some philosophers were still active. This meant the thread lifecycle was just as important as the chopstick synchronization. The main Dining Philosophers task needed to wait until all philosopher threads had completed before returning control back to the command-line portion of the project.

The thinking and eating behavior also had to be included in a way that made the threading behavior visible. Each philosopher alternates between thinking and eating, with both actions lasting for the required number of cycles. This creates different timing between the philosopher threads and makes the synchronization more realistic because they are not all requesting the chopsticks at exactly the same time. It also makes it easier to observe whether multiple philosophers are making progress or whether the program has become stuck.

For integration, Alan tried to keep his portion independent from the command-line code. Instead of making his own Main.java responsible for selecting tasks, he created the Dining Philosophers code so that Brendan could simply call DiningPhilosophers.run() when the user selects Task 1 with -A 1. This worked well with the way their responsibilities were divided, because he could focus on the threading and synchronization while Brendan focused on parsing the command-line arguments. Hans could then do the same with the Readers-Writers task. Keeping the tasks separate made it easier for them to work on different branches and combine everything later.

Overall, the main challenge of Alan's task was not just creating philosopher threads, but making sure all of those threads could safely share resources. He had to consider deadlock, shared data, the total meal limit, thread coordination, and integration with the rest of the program. The goal was to make the Dining Philosophers task work on its own while also keeping it organized enough that the rest of the group could build around it.

## Brenden Daigle, Command-Line Interface
---
For the command-line integration, Brenden created an src folder with a runnable main class. From there, he created a new application (configuration) used to provide command-line inputs consistent with what the project specified. The taskNumber int variable would specify which task (1 or 2) to run later, but it is initialized at -1 as a sentinel variable. The for loop first checks that “-A” is in the first spot of the arg; if not, it prints an error message and returns. Next, the program attempts to parse the value after -A, and if it fails, it prints an error message confirming that the value needs to be an integer. If the value was presented as an integer, but not 1 or 2, the program later handles that case by specifying so. After completing the for loop, the listed taskNumber will determine which class to run: the diningPhilosophers (1) or readersWriters (2).
There are multiple cases in which error-handling is covered. First, if there is a missing -A or an invalid argument, the program recognizes this, since it would have not finished the for loop with a changed sentinel value. In other words, taskNumber still being -1 would signal the program to output the error message “Error: Invalid or missing -A argument. Use: -A 1 (Dining Philosophers) or -A 2 (Readers Writers)”. The program also recognizes when there isn’t a value after -A, in which case it notes that -A requires a value (1 or 2). Lastly, if the user did provide input after -A, but it was not an integer, the program recognizes this and reminds the user that the next value must be an integer.
The integration with the other tasks was relatively simple, since our team members covering tasks 1 and 2 wrote their respective programs in separate classes. Therefore, all that was needed to run their programs was a call to the class itself. After the taskNumber is changed to 1 or 2, this signals the program to run whichever class is labeled with that number. For instance, if after the for loop a value of 1 is given to taskNumber, this executes Alan’s “run()” function within his program class.
